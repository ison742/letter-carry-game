# Letter Carry — README / Feature List

Letter Carry is a six-round word puzzle inspired by a chalkboard mockup. Each answer becomes the mandatory core of the next answer, growing from three letters to eight.

- **Play:** https://ison742.github.io/letter-carry-game/
- **Source:** https://github.com/ison742/letter-carry-game

## Feature list

### Core game from the initial brief

- Six horizontal answer rows containing 3, 4, 5, 6, 7, and 8 boxes.
- A bank of six unique selectable letters for every round.
- One system-selected hidden answer per round. Another valid word is still rejected when it is not the selected answer.
- Every letter in a solved word carries into the next round and must be used again.
- Carried letters are marked blue and labeled **carry**.
- Three fresh letters appear each round: one belongs in the answer and two are distractors.
- Three hints shared across the whole game, used in order:
  1. remove one distractor;
  2. reveal the answer's first letter;
  3. reveal its second letter.
- A complete 3→8 word chain, round progress, completion summary, and play-again flow.

### Manual follow-up features

These are the features I explicitly asked the agent to add after seeing the first playable version:

- **No-submit play:** a complete typed or clicked word checks automatically; Enter is unnecessary.
- **Previous attempts:** rejected guesses remain visible for the current word, together with the rejection reason.
- **Type-to-replace:** after a full guess is rejected, entering a new letter clears the old unlocked guess and immediately starts the next one.

I also supplied chalkboard reference images after the initial brief. The visual direction was revised into the current dark green board, chalk lettering, paper texture, blue carry tiles, and mint hint dock.

### Usability and engineering features

- Mouse, touch, and physical-keyboard input, with Backspace to undo.
- Clear, shuffle, restart, instructions, feedback, and hint-remaining controls.
- Responsive desktop and mobile layouts.
- ARIA labels and live regions for important controls and status changes.
- No framework, package, build step, or runtime dependency in the published app.
- Deterministic browser acceptance test covering the full six-round game.
- Automated desktop and mobile screenshots.
- Maintained `AGENTS.md`, project plan, README, live Git history, GitHub repository, and GitHub Pages deployment.

## Original prompt

The game began with this operator prompt, preserved here verbatim:

> Design a game:  horizontal rows of empty boxes that can contain letters: 3 boxes at the top row, 4 boxes on the row below that, 5 below that, down to the bottom row that has 8 boxes.
>
> on the side there is a panel of 6 unique  free letters generated by the system.
>
> 1. Round 1, the system picks a 3 letter word that can generated from the free letters. Even if the user selects a word that fits, it is incorrect. They guess untill they match the letters to the word that the system has selected.
> 2. Round 2, the letters from the previous 3 letter word are CARRIED OVER, and 3 new letters are provided. The 4 letter word must use all the letters that were carried over from the previous round, so the user has 6 letters to choose from, 3 that are marked in blue and must be used, these are the carry overs. Every subsequent round carries over all letters from. The letters that are not used in the solution word all called "distractors"
>
> There must be a hint bubble at the bottom which has 3 uses per game. The first hint removes one distractor, second hint shows the first letter of the word, third hint shows the the second litter of the word. ALl hitns can be used at once or not at all.
>
> Lets make this as an HTML web app and make it look good.

### How the counts were produced

The session substrate keeps an append-only transcript with timestamps, message roles, tool receipts, and cumulative token ledgers. The interval begins at the initial game prompt and ends when the repository, exact commit, and public Pages behavior were verified. The transcript contained 44 user-role records; two were automatically injected environment/context packets, leaving **42 human operator messages**. Of those, six carried direct game or delivery requirements: the initial brief, the visual references, the three follow-up gameplay changes, and the course publication brief.

The nearly 20-hour span is elapsed wall time, not active compute time. It includes overnight gaps, account setup, infrastructure discussion, operator availability, and deployment-policy repair. Likewise, the token total includes system instructions, cached context, tool payloads, and an unrelated architecture discussion that occurred in the same long-running thread. It should not be presented as the irreducible cost of this small game.

The runtime receipt exposes token usage but no defensible billed **USD** amount. This work ran in a subscription Codex session rather than as a directly metered API request, and cached-input pricing cannot be inferred safely from the transcript. For that reason, this report gives the auditable token cost and does not invent a dollar figure.

## What the substrate contributed

Here, **substrate** means the agent runtime around the coding model—not the game framework. It supplied identity, scoped work protocols, credential brokering, governed Git commits, append-only telemetry, and independent acceptance checks.

The interesting part was that the same session carried the work from a rough oral-style brief to a public artifact while preserving evidence at each boundary:

1. A verified agent identity attached the work to explicit BUILD protocols and exact file scopes.
2. The implementation stayed in a dedicated Git repository with an updated plan and `AGENTS.md`.
3. GitHub credentials were retrieved through a broker and used without printing or storing the token in the repository.
4. Commits were issued through commit authority instead of an unrecorded direct commit.
5. The published branch SHA was read back from GitHub.
6. A browser drove the local and public versions, checking rejection history, type-to-replace, automatic submission, carry-over rules, hints, restart, full completion, mobile overflow, and console errors.

That made failures more diagnosable, but it also exposed a tradeoff: governance and large persistent contexts are expensive in tokens. The 97.96% cache share softened repeated context processing, yet the raw total remains much larger than the application source. A useful next experiment would isolate the game task in its own thread and compare the same acceptance standard with a compact delegate context.

## Run locally

The app is static. Open `index.html` directly, or serve this directory with any static file server. With Deno and the standard file-server package:

```sh
deno run --allow-net --allow-read jsr:@std/http/file-server .
```

## Verify

The acceptance verifier launches a local static server and drives the full game in Chromium:

```sh
python3 verify_game.py
```

It checks the 3→8 row geometry, exact-answer behavior, carried letters, all three hints, complete playthrough, restart, mobile overflow, browser errors, and writes desktop/mobile screenshots under `artifacts/`.
